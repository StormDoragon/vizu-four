## Judgment rules

- Include substantive user-visible fixes, new capabilities, operational protections, licensing and useful new public guidance. Exclude test-only/CI-only work, housekeeping, roadmap sign-offs and duplicate merges.
- Flag concrete confidentiality/execution/availability risks and changes to protective or third-party-data boundaries for security review. Flag documentation/tests that disclose real vulnerability mechanisms even when excluded from notes. Ordinary UI errors, general policy notices and repaired invalid function names are not automatically security-sensitive.
- Mark breaking when an existing accepted and plausibly legitimate use now requires adaptation. The new accumulated configuration caps are marked breaking. Corrections toward the documented runner behavior and rejection of unsupported/malformed/excessive inputs are otherwise treated as fixes. This is a policy judgment, not a classifier-derived rule.
- Categories describe the primary shipped change; the security and breaking booleans are judged independently. Security fixes can also be breaking.
